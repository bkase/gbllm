# Foundation review

verdict: needs-work

## [high] Pre-tokenizer regex silently DROPS characters, so the core 'lossless / decode(encode(text))==text for any input' contract is false. The underscore '_' (and other Unicode connector-punctuation \p{Pc}) matches NONE of the alternatives: it is excluded from the letter class ` ?[^\W\d_]+` (explicit `_`), it is a \w char so it is excluded from the punctuation class ` ?[^\s\w]+`, and it is neither \d nor \s. `re.findall` skips unmatched spans, so the byte is lost. Verified with the shipped pattern: decode(encode('hello_world'))=='helloworld', '__init__'->'init', 'x_1'->'x1', 'a_b'->'ab'. Any snake_case identifier, markdown, or path underscore is corrupted. Because training used the same pretokenizer, the vocab never contains 0x5f except as base id 95, so the loss is doubly invisible (no token to inspect).

- where: training/gbtrain/tokenizer.py:35-36 (_PATTERN); manifested in encode() line 92-94 and the shipped pattern field in training/artifacts/tinystories_bpe_1024.json
- fix: Make the pretokenizer total. Append a catch-all so every remaining char lands in a chunk, e.g. add a final alternative `|[^\s]+|\s+` isn't enough since `_` is caught by neither — instead either (a) stop excluding `_` from the word class / add an explicit `|_+` (or `| ?[\w]+`-style) alternative, or (b) append a DOTALL catch-all `|.` as the last alternative with re.DOTALL. Then add an explicit round-trip test that includes '_', '__init__', 'snake_case', and assert '' == set(text) - set(''.join(findall)) over a fuzz corpus. Re-train/re-export the artifact after the fix (existing vocab is built on the lossy pretokenizer).

## [high] Cross-language parity is not achievable as specified: the pattern uses negative lookahead `\s+(?!\S)`, which Rust's `regex` crate (used by this repo — see /Cargo.toml and gbf-data/Cargo.toml) categorically does not support (no look-around). A from-scratch Rust byte-level encoder cannot compile the artifact's own `pattern` field. It would have to hand-roll a backtracking whitespace splitter that reproduces the GPT-2 'trailing whitespace run splits so the last space attaches to the next word' behavior (verified: '   word' -> ['  ',' word']; 'a  b' -> ['a',' ',' b']). Reproducing that backtracking by hand is subtle and a very likely source of divergent token ids, which silently corrupts inference.

- where: training/gbtrain/tokenizer.py:35-36 (`\s+(?!\S)`); consumed on-device via the `pattern` field in tinystories_bpe_1024.json
- fix: Replace the lookahead with a lookaround-free equivalent that BOTH Python `re` and the Rust `regex` crate compile identically (e.g. reorder so `\s+` only ever consumes runs not already claimed by the ` ?<class>` leading-space alternatives, or match whitespace-run-minus-last-space explicitly). Critically: do NOT rely on regex-string portability at all — ship a frozen conformance corpus of (text -> token-id) vectors next to the artifact and make the Rust encoder gate on byte-exact reproduction of those ids. Add the same vectors as a Python test so the two implementations are pinned to one oracle.

## [medium] Unicode class semantics are engine/Unicode-version dependent. Python `re` treats `\w`/`\d`/`[^\W\d_]` as Unicode for str using CPython's Unicode database; Rust's `regex` crate is also Unicode-aware but keyed to its own bundled Unicode version. For any non-ASCII input the split can differ (e.g. Arabic-Indic digits '٤٢' are captured by ` ?\d+` here; a Rust build on a different Unicode revision, or one compiled with `unicode-perl` disabled, splits differently), producing different chunk boundaries and thus different token ids than the Python encoder.

- where: training/gbtrain/tokenizer.py:35-36 (`[^\W\d_]`, `\d`, `[^\s\w]`, `\s`)
- fix: Pin the contract to explicit Unicode behavior: document the required Unicode version and required regex features, or (if the corpus is effectively ASCII) restrict the classes to ASCII ranges. Regardless, rely on the shipped text->ids conformance vectors (see prior finding) as the true parity gate rather than trusting `\w`/`\d` to mean the same thing in both engines.

## [medium] Encode merge algorithm is under-specified for a from-scratch Rust reimplementation. _merge_chunk is rank-greedy: each pass it scans the whole chunk, picks the globally lowest-rank mergeable pair, and merges only the LEFTMOST occurrence (strict `<` tie-break on position), then rescans. This is equivalent to canonical GPT-2 BPE, but a naive Rust port that instead does left-to-right positional greedy (merge the first mergeable pair encountered regardless of rank), or that merges all occurrences with a different tie order, will produce DIFFERENT ids on some chunks. The rank/leftmost invariant is load-bearing and is only implied by the code, not stated in the artifact.

- where: training/gbtrain/tokenizer.py:73-88 (_merge_chunk)
- fix: Document the canonical encode algorithm in the artifact/spec: 'repeatedly find the pair with the minimum merge rank; on ties in rank the pair is unique; merge the leftmost occurrence; repeat until no pair has a rank.' Back it with the shared conformance vectors including chunks that exercise overlapping and repeated best-pairs so a mismatched Rust order fails the gate.

## [medium] byte_cap / sample-mb slicing can cut a multibyte UTF-8 char mid-sequence, then `decode(errors='replace')` injects U+FFFD (ef bf bd), and the resulting truncated bytes are tokenized. This is deterministic but silently non-lossless at the boundary, and it means train/val streams can contain a spurious replacement token depending purely on the cap value. The same replace path in BPEModel.decode also means that during on-device GENERATION, any model-emitted token sequence whose concatenated bytes are not valid UTF-8 (e.g. a partial multibyte char at the render-buffer edge) is silently rewritten to U+FFFD rather than surfaced.

- where: training/gbtrain/data.py:28-33 (tokenize_file byte_cap slice), training/gbtrain/tokenizer.py:216-219 (_main sample slice) and tokenizer.py:96-98 (decode errors='replace')
- fix: Trim any byte-cap slice back to the last valid UTF-8 char boundary before decoding (scan backward off continuation bytes 0x80-0xBF). For on-device rendering, do incremental UTF-8 decoding that buffers a trailing incomplete char across token appends instead of emitting U+FFFD; document that decode() with errors='replace' is only safe on complete, encoder-produced streams.

## [low] from_json integrity check is incomplete: it uses obj.get('id_bytes_hex', {}), so a missing or truncated id_bytes table silently skips all cross-validation, and it never asserts len(id_bytes_hex)==vocab_size or that the declared vocab_size/base_vocab match the replayed model. A merge that references an out-of-range id crashes with KeyError rather than a clear error. For an artifact that 'silently corrupts inference' on mismatch, the loader should be stricter.

- where: training/gbtrain/tokenizer.py:125-138 (from_json)
- fix: Require id_bytes_hex to be present and to contain every id 0..vocab_size-1 (reject on missing/extra keys), assert obj['vocab_size']==BASE_VOCAB+len(merges) and obj['base_vocab']==BASE_VOCAB, and validate each merge pair (a,b) references only already-defined ids (< BASE_VOCAB+step) with a descriptive error instead of a bare KeyError.

## [low] On-device render-buffer sizing metadata is not exported. Feasibility itself is fine (1024 ids fit uint16/10 bits; id_bytes table is only ~3250 bytes total; longest token is 11 bytes: ' unexpected'), but the maximum token byte length that the Rust render/detokenize buffer must accommodate is not recorded in the artifact, so the Rust side has to compute it or risk under-sizing a fixed buffer.

- where: training/gbtrain/tokenizer.py:105-120 (to_json) and the artifact schema in tinystories_bpe_1024.json
- fix: Emit max_token_len (bytes) into the JSON (here 11) and have the Rust render buffer size from it; combine with the incremental-UTF-8 handling above so a token that ends mid-char is buffered rather than mis-rendered.
